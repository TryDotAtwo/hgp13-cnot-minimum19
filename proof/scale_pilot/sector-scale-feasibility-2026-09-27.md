# Ограниченный масштабный пилот q=2 и p=1

Статус: **измерительный пилот, не сертификат сектора**. Проверки ниже не
доказывают полноту prefix-таблиц, покрытие всех состояний или `NoShortProgram`.
Их цель — проверить формат и цену отдельных операций перед массовым экспортом.

## Данные и воспроизведение

- Исходный `outputs/hgp13-arxiv/hgp13_verify.cpp`: SHA-256
  `2174f445df534455c30e9ae7b54b8dfff4fdbdce3ff4eaf6b7d7e557fa3f8e4c`.
- `work/generate_sector_scale_samples.py` добавляет только вывод трёх
  фактически достигнутых состояний глубин 4, 8, 11 с наибольшим числом битов
  истории, их локальных преемников и одного терминала с минимальной полной
  ценой. Вывод: `work/sector_scale_0.log` и `work/sector_scale_315.log`.
  Хеши исходника инструмента и логов — в `work/sector_scale_samples.json`.
- `work/generate_sector_scale_lean_probe.py` переводит восемь 64-битных слов
  истории в один `Nat` без отбрасывания старших разрядов. Lean проверяет
  **точное равенство** `SharedSearch.next` спискам локальных преемников и
  `SharedSearch.terminal = true` на критических терминалах.
- `work/generate_sector_scale_potential_probe.py` предлагает таблицу
  `min(3, distance)` для каждой формы из полного 8- или 9-битного пространства.
  Lean в `SectorScalePotential0.lean` и `SectorScalePotential315.lean` проверяет
  `FullPackedPotential.check = true` для каждой полной исторической строки и
  каждого входа XOR, затем отдельно проверяет границу `18 < depth + sum`.
  Python BFS только предлагает таблицу; математическая нижняя оценка
  проверяется ядром. Проверка связи этих пилотных литералов со *всем* поиском
  не выполнена.
- `work/PrefixDeletionControlLite.lean`: ядро доказывает, что тройка
  `[9,11,22]` действительно `Catalogued`, её ключ `148886` есть в исходной
  таблице, а удаление этого ключа нарушает независимый предикат
  `FullWordPath.PrefixComplete`. Это отрицательный контроль интерфейса, а не
  проверка полной положительной таблицы.

Существующий образ `cnot-beam-torch:cu128` с `/usr/bin/g++` скомпилировал
ограниченный C++ экспортёр без сети и GPU. Lean 4.34.0 запускался в
`local/lean4:4.34.0` с лимитом 4 GiB. Основные команды: генераторы Python,
`g++ -O3 -std=c++17 -pthread sector_scale_samples.cpp -o sector_scale_samples`,
`./sector_scale_samples --one 0` и `--one 315`, затем
`LEAN_PATH=/scratch:/proof/.lake/build/lib/lean lean -R /scratch <probe>.lean`.
Файлы `work/` монтировались как `/scratch`, принятый Lean-проект как `/proof`.

## Наблюдения

| Случай | Фактические метки C++ | Терминалы | Лучшее C++ | Выборка истории на глубинах 4/8/11 | Проверенная Lean нижняя граница выбранного терминала |
|---|---:|---:|---:|---|---:|
| 0: две активные исходные координаты, два relay (`q=2`) | 2 500 086 | 436 | 19 | 13/17/20 форм | 19 (глубина 10, четыре стоимости 2+2+2+3) |
| 315: одна активная координата, один relay, есть slack (`p=1`) | 1 862 453 | 1 396 | 20 | 12/16/19 форм | 19 (глубина 6, пять весов 3+2+2+3+3) |

В обоих случаях локальные переходы и критический терминальный предикат
приняты Lean. Таблица потенциальных весов использует 1024 бита для `q=2`
и 512 бит для `p=1`; проверка прошла. Для `p=1` точная внешняя стоимость
выбранного терминала равна 20, тогда как усечённый потенциал даёт 19 —
этого достаточно для исключения длины ≤18, если терминал принадлежит
полностью проверенному графу.

Измерения Lean-процессов внутри отдельных Docker-контейнеров (wall по
`date`, CPU по разности `usage_usec`, peak по `memory.peak`) шумные из-за
чтения импортов с Windows bind mount. Все величины ниже относятся к
**отдельным локальным пробам**, а не к миллионам состояний:

| Проверка | Wall, наблюдённый диапазон | CPU в повторе | Peak RAM |
|---|---:|---:|---:|
| Только импорт исходного prefix-дерева | 7.5–11.8 с | 0.86 с | 145–150 МБ |
| Три перехода + терминал, `q=2` | 8.8–10.1 с | 1.68 с | 198–216 МБ |
| Три перехода + терминал, `p=1` | 8.4–12.7 с | 1.57 с | 196–202 МБ |
| Потенциал выбранного терминала, `q=2` | 6.8–15.5 с | 3.18 с | 299–328 МБ |
| Потенциал выбранного терминала, `p=1` | 6.2–10.9 с | 1.63 с | 193 МБ |

Исходное дерево префиксов имеет 864 774 байт Lean-кода и порождает
51 663 728 байт `.olean`; его компиляция заняла 18.4 с и достигла 1.12 ГБ.
Оно импортировало весь `SectorGraph359.olean` (69 100 928 байт) только ради
определения дерева. Экспериментальный `PrefixKeyTree.lean` отделяет это
определение; новая таблица имеет тот же размер `.olean`, компилируется за
19.4 с при пике 1.09 ГБ, а импорт без доказательств показал 5.9 с и
125 МБ. На проверках переходов пик снизился до 177/166 МБ, но wall вырос
до 15.4/18.0 с при сходном CPU: **устойчивого ускорения не установлено**.
Все локальные равенства с новой таблицей снова приняты Lean.

## Решение по масштабу

Пилот доказывает, что полные истории, местные `next` и терминальные
потенциалы практично проверять на выбранных состояниях. Он **не** доказывает
выполнимость проверки 2.5 млн / 1.86 млн меток и тем более всех 363
секторов. Ранее `Compact234Probe.lean` требовал 18 765 байт на 183 метки,
то есть около 103 байт исходника на метку. Прямая экстраполяция дала бы
около 258 МБ и 192 МБ Lean-исходника только для этих двух секторов, без
сертификатов терминалов и общего импорта. Это оценка формата, не замер
полного kernel replay. Текущий literal-подход не проходит критерий этапа D;
массовый экспорт не запускать. Следующий формат должен проверять целые
семейства/блоки компактнее, разделять общий lookup и предъявить замер
полного представительного блока до релиза.
